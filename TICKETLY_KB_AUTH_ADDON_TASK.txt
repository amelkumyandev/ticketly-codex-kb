AUTH ADD-ON TASK - Add JWT authentication and authorization using the knowledge base
-----------------------------------------------------------------------------------

Add authentication and authorization to the existing Ticketly API.

Follow:
- the architecture standards
- coding standards
- API standards
- QA standards
- security standards
- SonarQube standards
- token-burn tracking standards

Requirements:

1. Add user model and persistence.

Create an application user entity with:
- Id
- Email
- PasswordHash
- Role
- CreatedAt

Supported roles:
- Admin
- Customer

Architecture expectation:
- User persistence belongs in the data/infrastructure layer.
- Authentication workflows belong in application services.
- API endpoints/controllers should stay thin.
- Do not expose PasswordHash through API responses.

2. Add authentication endpoints.

Add:

POST /api/auth/register
POST /api/auth/login

Register request:
- Email
- Password
- Role

Login request:
- Email
- Password

Rules:
- Email is required.
- Password is required.
- Password must not be stored as plain text.
- Password must be hashed.
- Login returns a JWT access token.
- Invalid login returns 401 Unauthorized.
- Duplicate email registration should fail.

Security expectation:
- Use a password hashing mechanism suitable for application passwords.
- Do not invent reversible encryption.
- Do not log passwords or JWT tokens.
- Do not return PasswordHash in responses.
- Do not leak internal exception details.

3. Add JWT support.

Use JWT bearer authentication.

JWT should include:
- user id
- email
- role

Configuration should be read from appsettings or environment variables.

Use local demo settings if needed, but do not hardcode production secrets in source code.

Expected configuration keys:
- Jwt__Issuer
- Jwt__Audience
- Jwt__SigningKey
- Jwt__ExpiresMinutes

Security expectation:
- JWT signing key must come from configuration.
- README must clearly state demo secrets are local only.
- For Docker Compose, use environment variables.

4. Add authorization rules.

Protect the existing Ticketly endpoints:

Public:
- GET /health
- POST /api/auth/register
- POST /api/auth/login
- GET /api/events
- GET /api/events/{id}
- GET /api/events/{eventId}/ticket-types

Admin only:
- POST /api/events
- POST /api/events/{eventId}/ticket-types

Customer or Admin:
- POST /api/reservations
- GET /api/reservations/{id}

Implementation expectation:
- Use standard ASP.NET Core authorization policies or role-based authorization.
- Keep authorization readable and testable.
- Avoid custom security frameworks.

5. Update tests.

Add or update tests for:
- Register succeeds with valid data.
- Register fails for duplicate email.
- Login succeeds with valid credentials.
- Login fails with invalid credentials.
- Admin-only endpoint rejects anonymous users.
- Admin-only endpoint rejects Customer role.
- Admin-only endpoint accepts Admin role.
- Reservation endpoint rejects anonymous users.
- Reservation endpoint accepts Customer role.

QA expectation:
- Tests should have readable names.
- Include both success and failure paths.
- Keep tests deterministic.
- Update coverage.

6. Update coverage.

Run coverage command and update coverage notes.

7. Update README.

README must include:
- JWT configuration
- How to register a user
- How to login
- How to call protected endpoints with Bearer token
- Example Admin flow
- Example Customer flow
- Security limitations for demo use

8. Keep SonarQube support working.

Do not remove:
- docker-compose.sonarqube.yml
- scripts/run-tests-with-coverage.ps1
- scripts/run-sonarqube-analysis.ps1

If scripts need updates, update them.

Run:
- dotnet build
- dotnet test
- scripts/estimate-token-burn.ps1

If coverage script exists, run:
- scripts/run-tests-with-coverage.ps1

If SonarQube token is available, run:
- scripts/run-sonarqube-analysis.ps1 -Token "<token>"

If any command cannot run in the current environment, document the reason in EXPERIMENT_LOG.md.

Update:
- README.md
- TOKEN_BURN.md
- EXPERIMENT_LOG.md
- EXPERIMENT_RESULT.md

Stop after this task.
